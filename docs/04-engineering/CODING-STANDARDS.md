# 代码规范与 AI Agent 协作约束

> 版本:v0.2 最后更新:2026-07-22
> 本文件是 AI Agent 在本项目中生成/修改代码前**必读**的约束清单。目的是让不同时间、不同任务生成的代码保持一致的风格与质量底线。

## 1. 通用规范

- **TypeScript 严格模式**:所有包/应用 `tsconfig.json` 开启 `strict: true`;禁止使用 `any`(确需使用未知类型时用 `unknown` + 类型收窄),CI 的 lint 规则中此项为 error 级别,不是 warning。
- **禁止魔法数字/字符串**:评分权重、重试次数、限流阈值等业务常量必须来自配置文件或具名常量,不允许散落在业务逻辑中的裸数字(参考 `SCORING-SPEC.md` 4.3 节的要求)。
- **格式化与 Lint**:统一使用 ESLint + Prettier,配置文件纳入版本库,不允许个人风格覆盖团队配置。
- **提交信息规范**:采用 Conventional Commits(`feat:` / `fix:` / `docs:` / `refactor:` / `test:` / `chore:`),便于后续自动生成变更日志。
- **分支策略**:`main` 为可发布分支,功能开发走 `feature/*` 分支,通过 PR 合并;配置数据变更走 `config/*` 分支,同样必须走 PR(不因为"只是改数据"就跳过评审)。

## 2. 测试要求

| 代码类型                  | 覆盖率目标               | 说明                                                                                   |
| ------------------------- | ------------------------ | -------------------------------------------------------------------------------------- |
| `packages/scoring-engine` | ≥ 90%                    | 核心业务资产,必须覆盖 `SCORING-SPEC.md` 第 5 节列出的全部测试场景                      |
| `apps/api` 业务模块       | ≥ 70%                    | 至少覆盖 controller 的输入校验分支与 service 的主要业务分支                            |
| `apps/web`                | 关键交互路径需有集成测试 | 抽取按钮点击→展示结果、区间设定→抽取受限 两条核心链路必须有测试覆盖,不要求全量 UI 测试 |
| 配置数据                  | seed 约束校验(CI 强制)   | 见 `CONFIG-SCHEMA.md` 第 3 节                                                          |

- 遵循"先写测试再写实现"的原则(TDD)对 `scoring-engine` **强制要求**;其余模块推荐但不强制,视任务复杂度由 Agent 自行判断。
- 涉及"评分公式""区间抽取算法""留存率计算口径"的任何改动,提交前必须运行对应单元测试并在提交说明中体现测试通过状态,不允许仅凭代码审阅"看起来正确"就认为完成。

## 3. AI Agent 专属约束

1. **先查文档,再写代码**:实现任何功能前,必须先定位到 `03-spec/` 下对应的规范文件确认契约。如果规范文件没有覆盖当前需求的细节,应该:
   - 先在对应规范文件中补充定义(小范围、不改变已有契约的补充可以直接进行);
   - 若涉及已有契约的修改(如改变 API 响应结构、改变评分公式),必须先提出方案供确认,不能默默改契约再改代码。
2. **不允许跨越模块边界**:严格遵守 `DIRECTORY-STRUCTURE.md` 第 2 节定义的目录职责,例如不允许在 `apps/web` 里重新实现一遍评分计算逻辑。
3. **配置变更与代码变更分离提交**:一次 PR 尽量不要同时包含"业务代码逻辑变更"和"装备分数调整",便于评审与回滚(除非是"新增字段导致必须同时改 Schema 和加载逻辑"这种强耦合场景)。
4. **禁止静默假设**:PRD 中标注为"开放问题"的事项(见 `PRD.md` 第 8 节),已给出默认假设,Agent 应按默认假设执行,但如果发现默认假设与实际需求场景明显冲突,应先提出而不是自行改变假设继续往下写代码。
5. **变更记录义务**:修改任何 `docs/` 下的规范文件后,必须在该文件末尾的"变更记录"表格追加一行,写明日期与变更摘要;修改代码逻辑但未同步更新对应规范文件视为不完整的交付。
6. **提交前自检清单**(对应 Review Checklist,见第 4 节),Agent 在声明"任务完成"前应自行走一遍该清单。

## 4. Review Checklist(人工/Agent 自检通用)

- [ ] 代码变更是否有对应的规范文档依据?若规范文档需要更新,是否已同步更新?
- [ ] 是否运行了 lint / typecheck / 单元测试,且全部通过?
- [ ] 评分相关逻辑改动是否覆盖了 `SCORING-SPEC.md` 第 5 节的测试场景?
- [ ] 配置文件改动是否通过了 Schema 校验(权重之和、id 唯一性等)?
- [ ] 是否引入了新的外部依赖?如有,是否需要补一份 ADR?
- [ ] API 契约是否发生变化?如有,`API-SPEC.md` 是否同步更新,是否需要考虑向后兼容?
- [ ] 是否有硬编码的业务数值(分数、权重、阈值)混入代码逻辑?
- [ ] 是否涉及埋点事件的新增/修改?如有,`ANALYTICS-SPEC.md` 的事件清单是否同步更新?
