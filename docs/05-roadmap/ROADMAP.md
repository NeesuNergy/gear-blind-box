# 版本规划路线图

> 版本:v0.1 最后更新:2026-07-21
> 与 `PRD.md` 第 4 节功能范围、`ARCHITECTURE.md` 第 8 节架构演进对齐。本文件的作用是约束"每个阶段该做什么、不该做什么",避免 AI Agent 在实现某个版本时不自觉地引入超出范围的复杂度。

## MVP · V0.1(当前阶段)

**目标**:验证核心玩法(抽取+评分+区间筛选)可用,且埋点管道能跑通最基础的 PV/UV 统计。

**范围**:

- F1 随机装备抽取、F2 组合评分展示、F3 评分区间筛选抽取、F5 配置化数据(见 `PRD.md`)
- 基础埋点(`page_view` / `draw_triggered` / `draw_result_shown` / `score_range_set` 等事件采集与落库)
- 最小可用的内部统计查询(可以是直接查 SQL 或一个简陋的只读接口,不要求做可视化看板)

**明确不做**:

- 用户账号/登录
- 结果分享功能(F6,留到 V1.0)
- DAU/留存等聚合指标的自动化计算(先保证原始事件正确采集,V0.2 再补聚合计算)
- 管理后台(配置变更走 Git PR 流程,不做可视化编辑界面)

**验收方式**:对照 `PRD.md` 第 5 节各功能的验收标准逐条检查;评分引擎需通过 `SCORING-SPEC.md` 第 5 节全部测试场景。

## V0.2

**目标**:补齐数据度量能力,让"这个产品是否值得投入商业化"这一问题有数据支撑。

**范围**:

- 每日定时聚合任务,计算 `DailyMetricSummary`(PV/UV/DAU/新增/复访)
- 次日/7日/30日留存率计算(cohort 方法,见 `ANALYTICS-SPEC.md` 第 5 节)
- 评分区间预计算索引接入 Redis 缓存,提升区间抽取性能
- 补充基础错误追踪(接入 Sentry 或等价方案)与结构化日志

## V1.0

**目标**:提升传播性与用户粘性,为后续商业化探索埋点验证的功能形态。

**范围**:

- F6 结果分享:生成可分享的结果图片/卡片,便于社交媒体传播,分享行为埋点(`share_click`)
- 可选的用户账号体系(不强制登录,登录后可看抽取历史)
- 抽取历史记录页面(基于 `DrawRecord`)
- 匿名 ID 与账号 ID 的行为数据合并策略上线(见 `ANALYTICS-SPEC.md` 第 7 节)

## V1.5+(探索期,视 V1.0 数据反馈决定优先级)

**候选方向(不代表承诺一定做,需结合真实数据决策)**:

- 管理后台:可视化维护装备/干员配置,替代手改 JSON + Git PR 的流程,降低非技术运营人员的操作门槛
- 排行榜 / 社区精选组合:用户可以为抽取结果点赞/收藏,形成社区内容沉淀
- 商业化位:广告位、会员专属高级筛选(如多条件组合筛选、收藏无限制等)、与游戏内容相关的联运推广
- 分析存储升级:埋点原始数据量增长后迁移到 ClickHouse 等 OLAP 存储(见 `ARCHITECTURE.md` 第 8 节)
- 开放 API:允许社区第三方工具接入本站的装备配置数据/抽取能力(得益于 V0.1 就采用 REST 而非内部专用的 tRPC,具备迁移基础,见 `decisions/0001-tech-stack.md`)

## 阶段与指标对齐

| 阶段  | 关注的核心指标                                        |
| ----- | ----------------------------------------------------- |
| V0.1  | 功能可用性(是否符合验收标准),原始埋点事件是否正确采集 |
| V0.2  | PV/UV/DAU、次日留存率是否达到可持续运营的基本水位     |
| V1.0  | 分享率、复访率变化,验证"分享+历史记录"是否提升粘性    |
| V1.5+ | 结合真实用户行为数据,判断商业化功能的投入优先级       |
