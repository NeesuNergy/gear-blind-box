# PRD:GearBlindBox(装备盲盒)产品需求文档

> 版本:v0.2 最后更新:2026-07-22
> 状态:草案,待与项目发起人确认后冻结为 v1.0 基线

## 1. 背景

《三角洲行动》玩家在出装/配装时,经常需要在武器、头盔、护甲、干员之间做搭配决策。社区中存在"随机抽装备"的娱乐化玩法需求(类似"装备盲盒"),用于:

- 内容娱乐:主播/玩家用随机组合制造节目效果或挑战("用这套装备打完一整局")。
- 决策参考:通过评分快速判断一套随机组合的"强度",辅助玩家理解不同装备的价值。
- 社区传播:有趣的抽取结果天然具备分享属性(社交媒体二次传播)。

项目目标不是做一个一次性 Demo,而是构建一个**工程规范、可扩展、可度量商业价值**的产品雏形,为后续迭代(账号体系、分享裂变、商业化)打基础。

## 2. 产品目标

### 2.1 用户目标

- 一键随机抽取"武器+头盔+护甲+干员"四件套组合,获得即时的娱乐反馈。
- 看到组合的量化评分,直观理解这套装备的"强度"。
- 可以自定义想要的评分区间,只在该区间内抽取,提高抽取结果的可控性与重复可玩性。

### 2.2 业务目标(北极星指标)

初期(MVP)阶段没有商业化功能,但产品设计必须支持后续度量与优化,核心关注:

| 指标                     | 说明                     | 阶段 |
| ------------------------ | ------------------------ | ---- |
| PV / UV                  | 页面浏览量 / 独立访客数  | MVP  |
| 抽取次数 / UV            | 核心功能使用深度         | MVP  |
| 次日留存率(D1 Retention) | 反映内容是否有复访吸引力 | MVP  |
| DAU / WAU / MAU          | 活跃规模与增长趋势       | V0.2 |
| 7日/30日留存率           | 长期粘性                 | V0.2 |
| 分享率                   | 分享按钮点击 / 结果曝光  | V1.0 |

产品早期不追求功能复杂度,追求**"抽取体验爽快 + 数据可度量"**,为后续判断是否值得投入商业化(广告/增值功能/联运)提供依据。

## 3. 用户画像与场景

**主要用户**:《三角洲行动》活跃玩家,20-35岁,熟悉游戏内装备体系,常在游戏社群(QQ群/贴吧/小红书/抖音)获取攻略与娱乐内容。

**典型场景**:

1. 玩家开黑前无聊,打开网站抽一套装备"图一乐",截图发群里。
2. 主播直播时用随机装备做"整活"挑战,现场抽取增加互动性。
3. 玩家想了解某个评分段位的装备大概长什么样,通过区间筛选反复抽取对比。

| F1  | 随机装备抽取            | P0           | 一次抽取产出武器/头盔/护甲/干员四个位置的随机结果 |

- 商业化位(广告位 / 会员高级筛选 / 联运推广)

## 5. 详细需求与验收标准

### 5.1 F1 随机装备抽取

**用户故事**:作为玩家,我希望点击"抽取"按钮后,立刻获得一套随机的武器、头盔、护甲、干员组合。

**验收标准**:

- Given 用户在首页,When 点击"开始抽取"按钮,Then 页面在 1 秒内展示四个位置(武器/头盔/护甲/干员)各自的随机结果。
- 四个位置的随机结果各自独立抽取(不同位置之间没有强制关联关系,除非评分区间过滤生效,见 F3)。
- 抽取结果必须来自当前生效的配置版本中 `enabled: true` 的条目;已下架/未启用的条目不会被抽到。
- 同一装备类别下,如配置中定义了稀有度/权重字段,抽取概率应体现该权重(权重字段详见 `DATA-MODEL.md`);若未配置权重,默认等概率。

### 5.2 F2 组合评分展示

**用户故事**:作为玩家,我希望抽完之后能看到这套装备大概值多少分,以及每一项分别贡献了多少分。

**验收标准**:

- 抽取结果页展示一个 0-100 的综合评分(整数),以及武器/头盔/护甲/干员各自的单项评分。
- 评分计算逻辑必须完全依据 `SCORING-SPEC.md` 定义的公式与配置权重,业务代码中不允许出现魔法数字。
- 当配置数据版本更新(游戏版本变化导致强度调整)后,历史抽取记录展示的分数保持不变(记录当时的配置版本快照),但新抽取立即使用新版本分数 —— 保证"历史结果不因后续调整被篡改"。

### 5.3 F3 评分区间筛选抽取

**用户故事**:作为玩家,我希望能设定一个评分区间(例如 70-90 分),之后每次抽取只会得到落在这个区间内的组合。

**验收标准**:

- 用户可以通过滑块或输入框设定 `minScore` 与 `maxScore`(0-100,`minScore ≤ maxScore`)。
- 设定区间后,再次点击抽取,返回结果的综合评分必须落在 `[minScore, maxScore]` 闭区间内。
- 若设定的区间在当前配置数据下**不可能存在**任何组合(例如所有装备加起来都到不了 95 分以上),系统必须给出明确提示,而不是无限转圈或抽取失败无反馈(允许的实现方式与算法约束详见 `SCORING-SPEC.md`)。
- 区间筛选功能不应造成明显的等待感(交互响应目标 < 1.5 秒,含极端区间下的重试)。
- 用户清除区间设定后,恢复为全区间随机抽取。

### 5.4 F4 基础埋点

**用户故事**:作为产品负责人,我希望知道网站有多少人访问、多少人会回来、抽取功能到底有没有人用。

**验收标准**:

- 页面加载、抽取触发、区间设置等关键行为均产生结构化埋点事件(事件清单见 `ANALYTICS-SPEC.md`)。
- 埋点不依赖用户登录,通过匿名设备标识(anonymous_id)区分独立访客与复访行为。
- 埋点数据落库后,可以在（内部,非公开)统计视图中查到至少:当日 PV/UV、次日留存率、抽取次数分布。
- 埋点上报失败不能阻塞或影响主功能体验(异步、静默失败、允许丢失少量数据)。

### 5.5 F5 配置化装备/干员数据(工程需求)

**验收标准**:

- 武器/头盔/护甲/干员四类数据统一存放在数据库表 `gear_items` 中,字段与约束符合 `CONFIG-SCHEMA.md` / `DATA-MODEL.md`。
- 新增/调整某个装备的分数或参数,只需更新数据库中的对应行并 bump `config_revisions.versionTag`,不需要改动业务代码或重新设计评分公式。
- 配置数据在被服务用于抽取前必须经过约束校验(seed/CI + 运行时加载校验),校验失败禁止当作有效配置使用。

## 6. 非功能需求(概述)

详细指标见 `ARCHITECTURE.md` 的"非功能性需求"章节,此处仅列产品视角的约束:

- **性能**:抽取交互的用户可感知延迟应控制在 1.5 秒以内(含极端评分区间重试场景)。
- **可用性**:核心抽取与评分功能无需注册即可使用,降低使用门槛以利于早期数据积累。
- **数据合规**:埋点仅采集匿名化行为数据,不采集手机号/账号等 PII,须提供简单的隐私说明。
- **可维护性**:游戏版本更新后,应能在**不发版(或仅发布配置)**的情况下完成装备分数调整。

## 7. 范围之外(本轮不做)

- 不做用户账号、登录、第三方登录。
- 不做支付/商业化实际变现功能(仅预留埋点与架构扩展点)。
- 不做移动端 App(仅保证 Web 响应式适配移动浏览器)。
- 不做装备图片/模型的高保真还原(素材获取风险与版权问题超出本轮范围,MVP 阶段可用占位图/简化图标)。

## 8. 开放问题(Open Questions)

以下问题需要产品发起人在编码前进一步确认,已在对应位置给出默认假设,AI Agent 实现时按默认假设执行,若发起人给出不同结论需同步更新本 PRD:

1. 武器/头盔/护甲/干员四个位置的分数是否需要区分"细分类别"(如武器分步枪/狙击/冲锋枪)?—— **默认假设:V0.1 暂不区分细分类别,只做位置级别的四个槽位,细分类别作为配置字段保留扩展位。**
2. 单项评分的分数来源是否需要参考游戏内真实数值,还是完全由维护者主观打分?—— **默认假设:V0.1 采用维护者主观打分(0-100),后续可结合社区投票或游戏内数据校准。**
3. 是否需要限制同一用户短时间内的抽取频率(防止刷埋点/刷数据)?—— **默认假设:V0.1 增加基础速率限制(见 `API-SPEC.md`),防御性设计,不作为产品可见功能。**
