# ADR-0001:初版技术栈选型

> 状态:已采纳(Accepted) 日期:2026-07-21

## 背景

项目从零开始,需要在"尽快交付 MVP"与"为未来扩展留出空间"之间做取舍。核心约束:

- 团队规模小(甚至可能只有 AI Agent + 单一维护者),需要强约定、低歧义的技术选型。
- 核心业务逻辑(评分公式)必须可独立测试,不与框架强耦合。
- 早期没有真实流量压力,不需要为"高并发"过度设计。

## 决策

1. **采用 Monorepo(pnpm workspaces)**,而非前后端分仓库。
   理由:评分逻辑需要在前后端共享类型定义(至少共享 DTO 类型),分仓库会导致类型漂移和重复维护成本。
2. **后端采用 NestJS 而非更轻量的 Express/Fastify 裸框架**。
   理由:NestJS 的模块化、依赖注入、装饰器约定,能显著降低"不同开发者/不同时间生成的代码风格不一致"的问题,对 AI Agent 持续维护尤其友好。代价是初期有一定框架学习/样板代码成本,但换来长期一致性。
3. **评分核心逻辑独立为 `packages/scoring-engine` 纯函数包**,不放在 `apps/api` 内部。
   理由:评分公式是产品的核心资产,必须能脱离 HTTP/DB 上下文单独跑单元测试,且未来若要在前端做"预览分数"或迁移到其他运行时(如 Edge Function),可以直接复用。
4. **数据库采用 PostgreSQL,不引入 MongoDB 等文档库**。
   理由:抽取记录、埋点事件本质是结构化数据,后续聚合分析(留存计算、DAU 计算)天然适合 SQL;PostgreSQL 的 JSONB 字段足以覆盖"埋点属性是半结构化"这一诉求,不需要引入第二种数据库范式增加运维复杂度。
5. **装备/干员配置数据用 Git 版本化 JSON 文件,而非直接建数据库表**。
   理由:MVP 阶段没有管理后台,配置变更本质是"内容更新",用 Git 记录变更历史、走 PR 评审,比直接写库更安全、更可追溯。待 V1.5+ 引入管理后台后再迁移到数据库(见 `ARCHITECTURE.md` 第 8 节)。

## 备选方案与放弃理由

| 备选方案                                                 | 放弃理由                                                                                                                                                                                                    |
| -------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 前端用 Next.js API Routes 兼后端,不单独起 Nest 服务      | 短期最快,但会导致业务逻辑与前端框架强耦合,不利于未来独立扩展/拆分后端服务;评分逻辑是核心资产,值得单独立项                                                                                                   |
| 用 tRPC 替代 REST API                                    | 类型安全体验更好,但会让 API 变成"仅前端可用的内部契约",不利于未来对外开放数据/接口(如社区第三方工具调用);选择 REST + 显式 API 文档(`API-SPEC.md`)保留对外开放的可能性                                       |
| 用第三方 SaaS 分析工具(如 GA4/PostHog Cloud)替代自建埋点 | 上手快,但用户数据出境/数据归属存在合规与自主可控顾虑,且核心指标(如自定义的抽取行为、评分区间使用分布)用通用 SaaS 工具口径难以完全对齐;选择自建最小可行的埋点管道,后续如有需要可并行接入第三方工具做交叉验证 |
| 用 MongoDB 存埋点事件                                    | 团队/Agent 更熟悉 SQL 生态,且埋点数据后续必然需要做聚合分析,关系库 + 后续迁移 OLAP 的路径更清晰                                                                                                             |

## 影响

- 需要维护 pnpm workspaces 的构建配置,初期有一定 DevOps 成本。
- NestJS 的样板代码相对 Express 更多,但换来更强的可维护性,符合"AI Agent 长期维护"的项目诉求。
- 后续若要接入移动端 App 或第三方开放 API,REST 契约设计需要提前考虑版本化(已在 `API-SPEC.md` 中约定 `/api/v1` 前缀)。
